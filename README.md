# 📦 OOPS - 現代化品牌官網與後台管理系統

## 📋 專案簡介

OOPS 是一個整合 React 19 與 Firebase 的全棧實踐專案。本專案的重點不僅在於技術堆疊，更在於開發過程中如何透過**全鏈路設計思考**與**策略性 AI 協作**，將創意願景轉化為完整的系統解決方案。

---

## 🎯 核心功能

### 👥 前台用戶體驗

- ✨ **動態導航與視覺**：使用 GSAP 實作平滑滾動與視差效果
- 🔍 **即時產品展示**：從 Firestore 讀取資料，支援多分類動態篩選
- 📱 **響應式設計 (RWD)**：從手機到桌機提供一致的流暢體驗
- 📩 **聯絡表單系統**：串接資料庫實時紀錄用戶諮詢

### ⚙️ 後台管理系統

- 🔒 **身份驗證**：Firebase Auth 實作管理員登入與路由保護
- 📝 **實時 CRUD**：產品與活動資訊的新增、修改、刪除、上下架管理
- ☁️ **雲端媒體管理**：自動上傳圖片至 Firebase Storage 並自動優化快取

## 🧠 學習者的思考與挑戰

### 1. 技術選型策略：以實踐為導向的解決方案

在規劃 OOPS 時，我面臨了最大的技術挑戰：「如何在不具備後端開發經驗的情況下，實現一個完整的動態系統？」

**決策背景**：我清楚目前自己的技術邊界在於前端，若從頭學習傳統後端架構將會大幅延宕進度。

**選擇 Firebase 的原因**：為了達成「即時實現」的目標，我選擇了 Firebase 作為 BaaS 方案。這讓我能繞過伺服器架構，直接利用其成熟的 Auth、Firestore 與 Storage 服務。

**學習點**：這次經驗讓我學會「選擇正確的工具」。有效整合現有服務來達成目標，也是一種重要的開發能力。

---

### 2. 創意與技術的實作驗證

本專案的 UI/UX 設計稿由我自主規劃。

**驗證過程**：在設計階段，我會將視覺想像與 AI 進行反覆討論。這讓我能提前確認 GSAP 動畫等效果在技術上的可行性，縮短了設計與實踐之間的距離。

---

### 3. 架構思維：即使是新手也要做對的事

**Service Layer**：在 AI 建議下，我將資料讀寫邏輯抽離至 `services/`。即便語法是透過協作完成，但「讓組件保持乾淨」的架構意識，是我在這次專案中最實質的成長。

---

## 🚀 實戰中的問題解決

### 挑戰 1：Firebase vs. Axios —— 機制好奇與釐清

**探索**：最初不解為何 Firebase 不像 Axios 採用單次的「請求—響應」模式。

**理解**：釐清了 Axios (被動 Pull) 與 Firebase (主動 Push) 的差異。前者依賴重複請求獲取更新，後者則建立持久連線進行即時推播。

**收穫**：掌握「主動推播」如何消除延遲，讓網頁像即時通訊般流暢，這是在技術理解上非常重要的轉折點。

---

### 挑戰 2：表單送出的安全驗證 (reCAPTCHA v3)

**解決**：整合 Firebase App Check 與 reCAPTCHA v3。這次經驗讓我初步接觸了前端 API 防護，理解如何透過隱形驗證防止惡意填充。

---

### 挑戰 3：Firebase 全生態功能整合

**解決**：透過實作 CRUD 流程，我理解了雲端架構下，資料是如何從圖片上傳取得 URL，再存入 Firestore 紀錄的完整流向。

## 📂 專案目錄結構

```
src/
├── services/           # 資料處理邏輯：學習如何封裝 API
```
